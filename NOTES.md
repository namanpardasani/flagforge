# FlagForge Notes

Running log of decisions, tradeoffs, failure answers, and interview Q&A.

## Environment (Day 1)
- Windows + WSL2 (Ubuntu), repo at ~/flagforge
- Node, npm, pnpm via nvm; Docker Desktop with WSL integration
- Postgres: postgres:17-bookworm (Postgres 18 failed in this environment)
- Redis: redis:7 (Redis 8 failed in this environment)
- Docker Desktop proxy set to "No proxy" to fix Docker Hub pull errors
- Ports bound to 127.0.0.1 only, so nothing on the network can reach the dev DB

## Decisions
| Decision | Why |
|---|---|
| Postgres volume at /var/lib/postgresql/data | Postgres 17 stores data there; the old path bypassed the named volume |
| Rollout bucket = hash(flagKey + userId) mod 10000 | Finer than mod 100, allows 12.5% rollouts |
| Server-side SDK first, browser SDK later | Browser code is public, so full targeting rules would leak |
| SSE vs Socket.IO for SDK streaming | **SSE.** Updates only flow server -> SDK, so a one-way stream is enough. SSE is a normal HTTP response that stays open: no extra dependency, no handshake, passes through proxies/load balancers, and any language can implement a client with a plain HTTP library. Socket.IO adds a custom protocol, a client library and sticky-session needs for two-way messaging we do not use. Trade-offs accepted: text only, one direction, and browsers cap SSE connections per host (irrelevant for server SDKs) |
| Tenant integrity | Nothing in the DB prevents an Environment pointing at a Project from another workspace (workspaceId and projectId are separate columns). This is enforced in application code plus tenant-isolation tests. Implemented: projects are always fetched by {id, workspaceId}, and a new Environment copies workspaceId from that verified project (never from the request body). Possible later hardening: a composite foreign key (projectId, workspaceId) -> Project(id, workspaceId) so the DB itself rejects mismatches (needs a schema change). |
| Auth tokens | Access JWT (HS256, 15 min, algorithm pinned) plus opaque refresh token (7 days, stored as SHA-256 hash, rotated on each use; reuse of an old token revokes all the user's tokens). Refresh uses an atomic updateMany so two simultaneous refreshes cannot both succeed |
| Login errors | Same 401 for unknown email and wrong password, with a dummy bcrypt compare so timing matches. Register returns 409 on duplicate email (accepted enumeration trade-off for usability) |
| Tests use a separate DB | flagforge_test, guarded by name (must end in _test), tables truncated between tests; dev DB is never touched by tests |
| Redis is optional and never the source of truth | Postgres holds all state. Redis only holds a config cache, an API-key cache, rate-limit buckets and a pub/sub channel. Without REDIS_URL, or when Redis is down, the app keeps working (just slower, with per-instance limits and events). Connections fail fast (no offline queue, 250ms command timeout) so Redis trouble becomes a cache miss, not a hung request |
| Config cache correctness | Per environment: cfg:<env> (the cached /sdk/v1/flags body + version + etag) and cfgv:<env> (a marker = newest announced version, only ever increases). Entries are served only if version >= marker. Writers move the marker AFTER their DB commit and BEFORE publishing the event; a reader that loaded old data cannot cache it once the marker has moved (the put script refuses). All via atomic Lua scripts, so it is safe across instances. Result: a warmed SDK poll costs zero database queries |
| Why marker-before-publish matters | If the event went first, an SDK that refetches the instant it hears it could be handed the still-cached old entry. A test pins this ordering (found by mutation testing: it was not covered at first) |
| API key cache | Valid keys only, 60s TTL, value = ids (never the key or hash content). Revoking a key deletes it from the cache before anything else can use it; deleting an environment/project deletes its keys from the cache; the TTL is only a backstop. Cached keys never cross tenants because the entry carries the tenant ids |
| Rate limiting algorithm | Token bucket (burst up to capacity, refill capacity/window), run as one Lua script using Redis's own clock (so skewed server clocks agree and concurrent requests cannot both take the last token). Preferred over fixed windows (which allow 2x bursts at window edges). Keys are hashed so no emails/IPs sit in Redis |
| Rate limiting policy | Login: 5 tries per IP+account (then one more per 3 min) plus 30 per IP across accounts; register 10/h per IP; refresh/logout 60/min per IP; management API 600/min per IP; SDK: 3000/min per IP (guards the DB against unauthenticated floods), 1200/min per key for config polls, 6000/min per key for evaluate, 60/min per key for new streams. Limits run BEFORE validation so malformed requests cannot be spammed free. IP+account (not just account) means an attacker can only lock out themselves. A locked account refuses even the correct password (that is what makes brute force pointless) |
| Redis down -> limits still apply | The Redis limiter falls back to an in-memory limiter per instance: weaker (limits become per-instance) but never switched off, which matters most for login brute force. RATE_LIMIT_ENABLED=false turns everything off for load tests |
| Client IP and proxies | TRUST_PROXY = number of reverse proxies in front (Render, nginx). 0 means ignore X-Forwarded-For entirely (otherwise an attacker rotates the header to dodge limits); N means trust that many hops. Wrong value either way breaks limits: too low = all users share the proxy's IP, too high = spoofable. Must be set correctly at deploy time |
| Cross-instance events | RedisEventBus: delivery on the publishing instance is local and immediate (independent of Redis); Redis carries events to the other instances; messages carry the sender's id so an instance ignores its own echo (no duplicates). Incoming messages are validated (a JSON null payload used to crash the process: found by a test) |
| Pub/sub loses messages, so there is resync | Redis pub/sub stores nothing. While an instance's subscriber is disconnected it can miss events. The bus tracks health; when it drops, the server sends its SDKs a "degraded" event (they go back to normal-rate polling instead of the 5-minute safety net) and when it returns it re-sends hello(version) to every stream so SDKs compare versions and refetch if they missed anything. Found by a test: an instance with a dead Redis left its SDKs stale for up to 5 minutes |
| Shutdown cannot hang on Redis | redis.close() races QUIT against a 1s timeout and then force-disconnects. With Redis unreachable, QUIT sat forever behind queued subscribe commands and would have blocked graceful shutdown (found by a test) |
| Health endpoint | 503 only if Postgres is down. Redis down -> 200 with status "degraded" and redis:"down" (Redis is an optimisation, so a load balancer must not pull the instance) |
| Verified on the real process | Started the actual server against Redis: cache and key entries appear with the right TTLs, conditional GET returns 304, 6th wrong login returns 429 with Retry-After, and during a 3s Redis freeze (CLIENT PAUSE) health shows degraded, SDK polls and writes still succeed, the fallback limiter still blocks, and everything recovers by itself; SIGTERM exits in 0.11s |
| Stream is a doorbell, not a data pipe | The stream only says "environment X is now at version N"; the SDK then refetches through the ETag endpoint. The database stays the single source of truth, so a lost, duplicated or reordered event cannot corrupt anything; the SDK only compares version numbers. Pushing full configs would duplicate state, bloat fan-out and complicate auth |
| Config versioning | Environment.configVersion is bumped by one atomic UPDATE ... RETURNING inside the same transaction as the change (so version and data commit together, and concurrent changes never share a number). A flag create/delete bumps every environment of the project; a toggle/targeting change bumps one; renames and no-op saves bump nothing. /sdk/v1/flags reads the version BEFORE the flags: if a change lands in between, the flags are newer than the label and the SDK just refetches once more (the other order could label old flags with a new version and lose the update) |
| Events are published after commit | A listener that refetches immediately must see the change. Publishing is best-effort (failures swallowed): the change is already committed, and SDKs fall back to polling |
| No lost updates around connect | The server subscribes to the bus BEFORE reading the current version, queues anything that arrives meanwhile, sends hello(version), then sends queued events newer than the hello. Every connection starts with a hello, so a reconnecting SDK learns about changes it missed |
| SDK catch-up | An in-flight fetch that started before a change commits can return stale data, so after an event the SDK keeps fetching (up to 6 times, backing off) until it has the announced version. Bursts are coalesced. Hello with a DIFFERENT (even older, e.g. DB restored) version also triggers a resync |
| Stream resource limits | Heartbeat comment every 25s (keeps proxies from closing idle connections; the SDK treats 60s of silence as dead). Max 50 streams per key and 2000 total (429 beyond that, SDK falls back to polling). Slow consumers (64KB unread) are dropped. Revoking a key closes its streams immediately via the bus; streams also re-check their key every 60s, so a missed event or another instance still drops them. Shutdown ends all streams so server.close() cannot hang |
| Polling is a safety net while streaming | 5-minute poll while the stream is healthy, normal poll while it is down. Setting pollIntervalMs to 0 disables polling entirely and relies on stream + reconnect resync |
| Measured propagation latency | Median 24-26ms from the management API call to the SDK seeing the change (3 runs of 25 changes each, one local machine, includes the HTTP request itself). This is localhost only; real networks and a hosted free-tier server will be slower |
| Verified on the real process | Started the actual server on the test DB, opened a live SSE stream with curl, saw hello + change + heartbeat events over a real socket, then sent SIGTERM: the server exited in 0.11s and the stream client was disconnected (no hang from open streams). Note for scripts: signal the node process, not the npx/tsx wrapper |
| SDK evaluates locally | The SDK downloads the whole environment config and evaluates in-process with @flagforge/core: zero network calls per flag check, and flags keep working if the server is down. Trade-off: changes reach SDKs on the next poll (30s default) until real-time push (Phase 8) |
| SDK availability over freshness | Server outage after a successful fetch: keep serving the last config. Startup outage: on-disk copy -> bootstrap -> caller's default. Invalid/garbled responses never replace a good config. 401/403 stop polling (a revoked key must not hammer the server) but the last config keeps serving |
| SDK polling | setTimeout chain (not setInterval) with +-10% jitter, exponential backoff capped at 5 min while failing, unref'd timer so polling never keeps a process alive, one in-flight request shared by concurrent refresh() calls |
| SDK safety | Refuses to send the API key over plain http to non-local hosts. Error messages never include the key or URL. FileStorage writes 0600 and atomically (temp file + rename). evaluate() never throws; defaultValue is used only when no decision is possible (a known OFF flag returns false) |
| Conditional GET is hand-written | Express's built-in ETag check never returns 304 when the client sends Cache-Control: no-cache, and Node's fetch adds that header automatically to any request with If-None-Match. Found by the end-to-end SDK test (the SDK's own stub server had hidden it). /sdk/v1/flags now computes a content ETag and compares If-None-Match itself (weak validators, lists, *) |
| Evaluation lives in packages/core | Pure, dependency-free functions (hash, condition matcher, evaluateFlag) shared by the server and every SDK, so they cannot disagree. A server test proves /evaluate equals running core locally on the downloaded config |
| Evaluation order | Kill switch (disabled -> false) -> rules in order, first match wins, each with its own rollout -> fallthrough rollout. Boolean flags only for now |
| Bucketing | bucket = murmur3("flagKey:userKey") mod 10000; user is IN a rollout when bucket < bps (exclusive). Pure-JS hash (no node:crypto) so browsers get identical results. Buckets are pinned in tests: changing the hash would reshuffle every user. Flag keys cannot contain ":" so key/user boundaries never collide. Verified against published test vectors and an independent Python implementation |
| Rollouts are monotonic | Same user, same flag, same bucket: raising 10% -> 20% only adds users. Different flags bucket independently |
| Missing attributes | A missing attribute never matches any operator, including not_equals/not_in ("unknown user" must not satisfy a negative rule). No type coercion (5 != "5"). Attribute lookup uses own properties only (no "constructor"/"__proto__" surprises) |
| Targeting storage | FlagState.rules is JSON in core's Rule shape, fallthroughBps an int (basis points, 12.5% = 1250). Management API speaks percentages (max 2 decimals); SDK payload speaks bps. Input is strictly validated (operator/value type pairs, max 20 rules, 10 conditions) and re-validated when read back |
| Targeting audit | flag.targeting_updated stores before/after rules and rollout; toggles stay a separate flag.toggled entry; no-op updates log nothing |
| SDK endpoints | GET /sdk/v1/flags (full config for local evaluation), POST /sdk/v1/evaluate, POST /sdk/v1/evaluate-all. All authenticated by API key; tenant/project/environment come from the key, never the request |
| Default environments | Creating a project also creates dev, staging and prod in the same transaction (a project never exists half-built). Environments are ordered by (createdAt, id) because rows inserted together can share a timestamp |
| API keys | Format ff_ + 192 random bits, one key per environment. Only the SHA-256 hash is stored (fast hash is fine because keys are random, unlike passwords). The full key is returned once at creation; lists show only a prefix. ADMIN+ manage keys. Revocation is immediate (checked on every request). The key itself identifies tenant + environment, so SDK calls need no workspace id and cannot cross tenants |
| Two auth schemes | User JWT for the dashboard/management API, API key for /sdk/*. Neither is accepted on the other's routes |
| Flags model | Boolean flags per project. FlagState holds one row per (flag, environment); no row means off, so new environments need no backfill. Flag key is unique per project and immutable. Flag/FlagState/AuditLog all carry workspaceId and every query filters on it |
| Flag permissions | Read: VIEWER+. Create/edit/toggle: MEMBER+. Delete flag and read audit log: ADMIN+ |
| Audit log | Each change writes an AuditLog row in the same DB transaction as the change (all or nothing). Toggles are logged only when the value really changes. actorId is SET NULL if the user is deleted, so history survives |
| Project/environment permissions | Read: VIEWER and up. Create/delete projects and environments: ADMIN and up (structure changes are rarer and riskier than flag edits, which MEMBER will get later) |
| Workspace permissions | Roles OWNER > ADMIN > MEMBER > VIEWER, enforced by requireWorkspaceRole middleware on the backend. Non-members get 404 (not 403) so other tenants' workspaces are invisible. Only OWNER grants/revokes/removes ADMIN; OWNER cannot be assigned, changed or removed (transfer is a later feature); members can leave. Member targets are looked up by (workspaceId, userId), so ids from other tenants are "not found" |
| Dashboard API client | One module (apps/web/src/api/client.ts) does all HTTP. Responses are checked with Zod and converted to the app's own types in adapters.ts, so an API change touches one file. Errors become one ApiError type (status, code, message, request id); status 0 means "could not reach the server" |
| Where the browser keeps tokens | Access token (15 min): in memory only, never in storage. Refresh token (7 days): localStorage, so a reload does not sign you out. Trade-off accepted for now: a script injected by XSS could read the refresh token. Rotation plus reuse detection limits the damage, but an httpOnly cookie would be stronger and needs a server change (see Open items) |
| Refresh on 401 | The client refreshes ONCE and repeats the request ONCE; a second 401 ends the session instead of looping. Refresh tokens are single-use, so refreshes are serialised: one shared promise per tab, and a Web Lock across tabs with the stored token read only after the lock is held. Without that, two tabs would replay the same token and the server would revoke the whole family. A refresh that fails for a temporary reason (503, offline) keeps the session |
| Dashboard live updates | New endpoint GET /workspaces/:id/projects/:id/stream: SSE for a signed-in user (the SDK stream needs an API key, which the dashboard does not have). Same doorbell idea: hello with every environment's version, then change {environmentId, version}. It carries no flag data, so any member may listen; the data is refetched through the normal role-checked routes |
| Dashboard stream access | Does not outlive its grounds: the stream ends when the access token that opened it expires (the client reconnects with a fresh one), and membership and project are re-checked on a timer, so a removed member loses it. Max 10 streams per user. Non-members get 404, as everywhere |
| Why fetch and not EventSource | EventSource cannot send an Authorization header, so the token would have to go in the URL and end up in logs. The dashboard reads the response body by hand instead |
| Row flash without knowing who changed what | The stream only says an environment moved. The dashboard refetches the flags, compares each row with what was on screen, and flashes those that differ. A change you made yourself is already in the cache (optimistic update), so it compares equal and is not shown as someone else's |
| Reconnect and resync | Any end of the stream reconnects with exponential backoff (1s to 30s) and jitter; 60s without a heartbeat counts as dead. Every connection starts with hello: if a version differs from the last one seen, something was missed and the flags are refetched. While the stream is not live, the flag list also polls every 15s |
| Last environment is protected | DELETE of a project's only environment is a 409 LAST_ENVIRONMENT: a project with none has nowhere to keep flag state. The check is count-then-delete, so two simultaneous deletes of the last two environments could both pass; accepted (leaves an empty project that can get environments again) |
| Environment changes reopen the dashboard stream | The stream effect depends on the loaded project, so creating or deleting an environment (which refetches the project) reconnects the stream with the new set |
| Audit log paging | GET /workspaces/:id/audit-log takes limit (max 100) and before=<id of the last entry seen>, and returns { entries, nextCursor }. Newest first, ordered by (createdAt, id) so entries with the same timestamp never repeat or vanish between pages. The cursor is looked up inside the caller's workspace, so another tenant's entry id is a 400. One extra row is fetched to know whether another page exists, instead of a count query |
| Revocation names the key | The apikey.revoked audit entry records the key's name and prefix (never the secret or hash), so the log can say which key was revoked |
| Demo app (apps/demo) | A pretend shop that uses the real SDK. The API key and SDK live in the demo's SERVER; the browser gets only decisions (value, reason, rule id) over the demo's own SSE stream, never the rules or the key. On the SDK's "update" event the server re-evaluates for each connected viewer's sample user and pushes a snapshot. Plain node:http, no framework: three routes and a stream |
| Demo app hardening | Only GET; the one input (which sample user) is validated against a fixed list with Zod; strict Content-Security-Policy with no inline script or style (page, CSS and JS are separate URLs); the browser script writes with textContent only; binds to 127.0.0.1 by default; config errors name the variable but never print its value |
| Demo propagation, measured | Flag flipped through the management API to the new answer arriving on the demo's browser stream: 21 to 32 ms over 6 flips, one local machine, no Redis (2026-10-11). Includes API request, DB commit, SDK stream event, SDK refetch, re-evaluation and the push. Local only; a hosted setup will be slower |
| Production build of the server | esbuild bundles our own code and @flagforge/core into one dist/server.js; npm packages stay external and load from node_modules. Needed because workspace packages are TypeScript source, which Node cannot run from a dependency. Verified by starting the bundle with NODE_ENV=production and exercising auth, flags, SDK evaluation and CORS |
| CORS allow-list | CORS_ORIGINS lists the exact browser origins allowed. Unset means any origin in development and NONE in production, so a forgotten setting fails closed. No credentials permission is sent (tokens travel in a header). CORS is not access control (routes still need a token or key); it stops other websites from using a visitor's browser to call the API. Entries are validated at startup (must be an origin: no path, no trailing slash, no wildcard) |
| CI | GitHub Actions on every push and pull request: typecheck, lint, tests and builds for all five packages, against the same PostgreSQL 17 and Redis 7 images as development |
| Server-side evaluation shares the config cache | /sdk/v1/evaluate and /evaluate-all use the same cached JSON as /sdk/v1/flags, parsed once per environment and reused while the ETag is unchanged (bounded to 500 environments). They therefore answer exactly what a polling SDK would compute, with the same freshness rule (the cache refuses entries older than the announced version), and a warm environment costs no database query |
| Experiments model | An experiment is an A/B test on ONE boolean flag in ONE environment. Users who get the flag are treatment, the rest control: the flag's existing rollout is the split, so no second assignment mechanism exists that could disagree with it. Statuses DRAFT -> RUNNING -> STOPPED; a stopped experiment cannot restart (its data would mix two periods) |
| One running experiment per flag and environment | Enforced by a partial unique index written by hand in the migration (Prisma cannot express one). Two people pressing Start at the same moment: the database lets exactly one through (tested) |
| Experiment storage: one row per user, hashed | ExperimentExposure and ExperimentConversion hold one row per user per experiment, keyed by sha256(experimentId + ":" + userKey). No raw events (they would outgrow the free 0.5 GB database), and no application user ids: the hash is per experiment, so rows cannot be linked across experiments. First variant seen wins (INSERT ... ON CONFLICT DO NOTHING); a conversion counts once and only for a user already exposed |
| Experiment events | POST /sdk/v1/events with an API key, up to 500 events per batch, 600 batches a minute per key. The environment comes from the key, never the request. Events for flags or metrics with no RUNNING experiment are accepted and ignored, because an SDK cannot know which flags are under experiment |
| Experiment statistics | Two-proportion z-test and 95% interval from packages/core (pure, tested against an independent Python computation). No verdict below 100 users per group or when conversions are too rare for the normal approximation. It is a fixed-horizon test: peeking daily and stopping at the first "significant" result inflates false positives, and the UI should say so |
| Sample ratio check | Compares the observed treatment share with the rollout percentage (chi-squared, p < 0.001 = mismatch). Skipped when the flag has targeting rules, because the expected share then depends on user attributes the server never sees. The variant is reported by the SDK and trusted: the API key holder is the tenant's own server |
| SDK experiment events | Opt-in (`sendEvents`), so no user key leaves a server unless asked. Exposure = a real decision from evaluate/isEnabled, reported once per (flag, user) while the pair is remembered (bounded to 20,000, oldest forgotten first) and again if the value changes. allFlags is NOT an exposure: listing every flag is not showing it. Conversions come from track(). Events queue in memory and are sent in batches of 500 on a timer, so a flag check never touches the network; failures (network, 429, 5xx) retry, a 401/403 drops the queue and stops reporting with one fatal error, other 4xx drop the batch; the queue is bounded (default 10,000, oldest dropped and counted). Known limit: a process that exits without flush() loses its queue |
| Demo app and experiments | The demo's SDK runs with sendEvents on. Watching the shop is an exposure (the featured flag is asked for with evaluate, which records it; the table of other flags uses allFlags, which does not). POST /pay records a conversion; POST /simulate sends 1 to 1000 pretend shoppers who are exposed and pay at 10% (card form) or 14% (one-tap). Those rates are invented and are shown as invented on the page. The two POST routes accept only JSON from the same site (Content-Type and Origin checks, because a page on another website can make a browser send a form POST to localhost), with strict Zod bodies and a 2 KB cap |
| Verified on the real stack | Real API, PostgreSQL, Redis and the real demo app and SDK: 3,000 simulated shoppers gave 1,480 control and 1,521 treatment users (50.7% treatment against 50% expected), conversion 8.4% against 13.7%, +5.4 points, p about 3e-6, verdict "treatment better". The control rate came in under the planted 10%, which is ordinary sampling noise at this size (about two standard errors); the planted 4-point lift lies inside the reported 95% interval (3.1 to 7.6) |
| Emailed tokens | Verification and reset links carry a random 256-bit token; only its SHA-256 hash is stored (a database leak gives no usable link). Single use, claimed with an atomic UPDATE ... WHERE usedAt IS NULL AND expiresAt > now (two simultaneous clicks: one wins, tested). Asking for a new one retires the old ones. Verification lasts 24 hours, reset 60 minutes |
| Token in the URL fragment | Links look like https://app/reset-password#token=... The fragment is never sent to any server, so the token cannot land in access logs, proxy logs or a Referer header; the page reads it with JavaScript and removes it from the address bar. A query string would leak it to all of those |
| Forgot password reveals nothing | Always 202 with the same body for known and unknown addresses. The lookup and the email run in the background, so response time does not tell either. Limited per IP (5/hour) and per address (3/hour) so neither the endpoint nor one inbox can be flooded. Accepted gap: the unknown-address path does less database work than the known one, a difference of a few milliseconds that the background work hides but does not remove |
| Reset signs everyone out | Setting a new password revokes every refresh token, retires other reset links, and marks the address confirmed (receiving the email proves it). A "your password was changed" email goes to the address so an attacker's reset is noticed. Access tokens already issued live out their 15 minutes; that is the cost of stateless JWTs |
| What verification enforces | Adding a member by email requires the target's address to be confirmed (409 EMAIL_NOT_VERIFIED): the feature trusts that an address belongs to the person you mean. Signing in and using flags do NOT require it, so first-run setup has no friction. The dashboard shows a banner with a resend button |
| Email is behind an interface | Mailer.send(). LogMailer (development: writes the message, link included, to the server log), BrevoMailer and ResendMailer (plain fetch to their HTTP APIs, so no new dependency), MemoryMailer (tests). Config refuses MAIL_PROVIDER=log when NODE_ENV=production, because the links are secrets and a log is not private. Provider errors never include the API key or the message body. Sending is best effort and in the background: a broken provider cannot break registration |
| Free email tiers | Brevo: 300 a day, delivers to anyone after you verify one sender address (no domain needed). Resend: free, but delivers only to addresses on a domain you have verified. For a portfolio project without a domain, Brevo is the practical choice |
| Scheduled rollouts | "At this time, apply this change to this flag in this environment." The change has the SAME shape and validation as a normal flag-state update (the schema is reused, nested under `change`) and is applied through the SAME service method a person's click uses, so the audit entries, the configVersion bump and the stream to SDKs are identical. A ramp ("10% Monday, 50% Wednesday, 100% Friday") is simply several scheduled changes. Time must carry an offset (a bare local time depends on the server's zone and is refused), at least 1 minute ahead and at most a year; at most 20 waiting per flag and environment |
| How due changes are claimed | One UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING, using the DATABASE's NOW() (instances with different clocks still agree). Each row is taken by exactly one runner, tested with two concurrent runners and six due changes. A claim that is never finished (the process died) is taken over after 5 minutes: safe, because a change sets absolute values and repeating one is harmless. Runs in the API process every 15 s, with a catch-up pass at start-up |
| A scheduled change re-checks its author | Days may pass between planning and running. At run time the creator must still be a workspace MEMBER or higher; otherwise the change FAILS with the reason (visible in history and the audit log) and the flag is untouched. The stored patch is validated again too, so a row edited by hand cannot bypass the rules. Cancelling only affects PENDING rows (the condition is inside the UPDATE), so a change being applied cannot also be cancelled |
| Scheduled changes on a sleeping host | The runner lives in the API process. On Render's free tier the process sleeps after 15 minutes without traffic, so a change due at 09:00 runs when it next wakes. Mitigations: a free uptime monitor hitting /health every 5 minutes (stays inside the 750 free hours for one service), and the start-up catch-up pass. The honest alternative is a separate scheduler service, which the free tier makes awkward |
| Role-based hiding | The UI hides or disables what the role cannot do (viewer: no toggles; non-admin: no audit request). That is convenience only. If the server answers 403 anyway (role changed since the page loaded), the optimistic change is rolled back and the server's reason is shown |
| Rule editing vs the API's rule shape | The server stores rules with several AND-ed conditions and typed values; the form edits one condition as text. Extra conditions are shown read-only and saved back untouched. A value that was not edited is sent back exactly as received (so numbers and booleans keep their type); a value typed in the form is sent as text, a list for "one of", or a number for comparisons |
| Web tests use a fake server, not mocked functions | apps/web/src/test/fake-server.ts speaks the real wire format (ids, error bodies, single-use refresh tokens, SSE) and is plugged in as the client's fetch. The tests therefore run the real client, adapters, hooks and stream code |

## Free-tier limits (checked 2026-10-09)
| Service | Limit | Implication |
|---|---|---|
| Neon (Postgres) | 0.5 GB storage, 100 CU-hours/month per project, scales to zero after 5 min idle, 6h restore window | Aggregate experiment events; first query after idle is slow |
| Upstash (Redis) | 256 MB, 500K commands/month, 10K cmds/sec | Run k6 against local Redis only; keep pub/sub and rate-limit commands lean |
| Render (backend) | 750 instance hours/month per workspace, sleeps after 15 min idle, cold start ~15s or longer | SSE drops on sleep; SDK must reconnect and resync; warm up before demos; keep a video |
| Vercel (frontend) | Hobby: 100 GB transfer, 1M edge requests, non-commercial only | Fine for a portfolio project |
| Fly.io | 7-day trial, then card required | Dropped |

What the runs showed:

- **The poll path is cheap**, as designed: a warmed environment is served from Redis with no
  database query, and held 1000 requests a second.
- **Server-side evaluation was reading PostgreSQL on every call.** Before the fix it saturated at
  about 880/s with a p95 of 2.1 s at a 1000/s target. It now evaluates against the same cached
  configuration the poll endpoint serves (parsed once per ETag), and holds 1000/s with a p95 of
  25 ms. Found by this load test, not by reading the code.
- **The dashboard flag list is bound by the database**: about 340 requests a second on this machine
  (membership check, project check, flags and environments are four queries per request). That is
  far more than people clicking can produce, so it is left uncached on purpose: the dashboard must
  always show what the database says.
- The poll being faster at 1000/s than at 200/s is real, not an error: at higher rates connections
  and the event loop stay warm.

## Open items
- Scheduled changes are not undone automatically: to "turn on for a week" plan two changes (on, then off). There is no recurrence and no timezone picker beyond the browser's own.
- Experiments: one metric per experiment, conversion counted as yes/no per user (no revenue or counts); no sequential testing, so results should be read once at a planned sample size; changing the rollout percentage while an experiment runs is allowed but muddies the split check.
- Members can only be added if they already have an account (and have confirmed their address); there are no email invitations. The mail sender now exists, so invitations would be a small addition: an invite token like the reset token, accepted after sign-up.
- Deleting an environment asks for a hold, not for typing its name; fine for a portfolio project, worth upgrading for real use.
- Refresh token is in localStorage (readable by injected scripts). Stronger: an httpOnly, Secure, SameSite cookie set by the server, with the refresh route reading it. Needs server changes and CSRF thought; do before real users.
- The dashboard treats environments with key "prod" or "production" as needing hold-to-confirm. The server has no "is production" field, so a production environment with another key is not guarded.
- The flag form cannot create a rule that compares against a number or boolean with "is" (typed values are sent as text). Possible through the API; a type picker in the form would fix it.
- Dashboard screens still to build: members, environments, API keys, full audit log (the API for all of them exists).
- The in-memory event bus and per-instance rate limits are only used when REDIS_URL is unset; with Redis, events, caches and limits are shared across instances (see Phase 9 decisions).
- There is no negative cache for API keys, so a flood of INVALID keys costs one Postgres lookup each; the per-IP SDK limit (3000/min) bounds it. If that ever matters, add a short negative cache.
- If someone edits the database by hand (bypassing the API), the config cache stays stale until its 1h TTL, because only API changes bump the version and move the cache marker.
- On a free-tier host that sleeps when idle (Render), open streams drop when it sleeps; the SDK reconnects and resyncs via hello when it wakes.
